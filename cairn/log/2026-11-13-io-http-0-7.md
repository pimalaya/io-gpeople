# io-http 0.7

The crate moves from io-http 0.6 to 0.7.0, and its dev-dependency io-oauth from 0.5 to 0.6.0, itself on io-http 0.7, so a single io-http resolves in the graph. The lockfile follows io-oauth 0.6 onto rsa 0.10.0 and loses rand and chacha20. Nothing had to change to compile: the crate hands `HttpRequest` values to `Http11Send::new`, which stays infallible, and it never called `to_http_11_vec`, the event stream parser or the `Display` of `HttpAuthBearer`. tests/people.rs compiles unchanged against the JWT bearer client of io-oauth 0.6.

Breaking for consumers all the same: the coroutines take io-http's `HttpAuthBearer` and `GpeopleSendError::Send` carries its `Http11SendError`, so a consumer moves in step.

Two things were adopted with the bump, both left for it by the family audit of 2026-11-13.

**A request that would split.** `GpeopleSend::with_method` builds the `Authorization` header from the caller's token and takes a method and a content type as they come. Against io-http 0.6, a token holding a line break was written as is: `a_token_holding_a_line_break_never_reaches_the_wire` showed `Authorization: Bearer fake-token`, CR, LF, `X-Injected: 1` on the wire. io-http 0.7 validates the head when `Http11Send` is built and fails its first resume, nothing written. No code was added for it: the refusal already reaches the caller typed, as `GpeopleSendError::Send(Http11SendError::InvalidRequest(_))`, through the existing `From`, and as `GpeopleClientStdError::Send` from the std client. The constructors stay infallible on this point, as `Http11Send::new` does.

**The path helper (FAM-11).** `resource_url` in src/v1/send.rs keeps what is its own (the collection check, the refusal of an id that is empty, `.` or `..`, the `:method` suffix glued to the id before the push) and hands the segments to io-http's `rfc3986::path::http_url_build` instead of pushing them itself. Every request the scripted tests pin is unchanged, the ten paths of `a_resource_id_is_one_path_segment` included. One behaviour moved, and it was a defect: the URL parser strips tabs and line breaks from a pushed segment, so `people/.`, tab, `.` given to `GpeoplePersonGet` passed the dot check and was then resolved as `..`, the request going to `GET /v1/` (`rejects_a_resource_id_holding_a_tab_or_a_line_break` failed with exactly that), and `people/c`, LF, `1` reached `people/c1`. The helper refuses such a segment, which `resource_url` reports as `GpeopleSendError::InvalidRequest` like any other name outside `<collection>/<id>`. The helper's other error, a base URL that does not parse, cannot happen with the constant base and maps to `GpeopleSendError::ParseUrl`, as before.

What the HTTP layer now does under the coroutines, unchanged code: interim 1xx responses are skipped, up to 8; chunk data without its CRLF fails, trailers are read and dropped; a final transfer coding other than `chunked` fails; an HTTP/1.0 response keeps the connection only on the `keep-alive` option. No scripted test pinned any of it and none was edited.

Capabilities moved: requests (one requirement modified, the id of a resource name holds no tab and no line break; one added, a request that would split is never written).

Verified: in tests/coroutines.rs, `a_token_holding_a_line_break_never_reaches_the_wire` fails against io-http 0.6 and passes, `rejects_a_resource_id_holding_a_tab_or_a_line_break` fails against the previous `resource_url` and passes. `cargo test --all-features` passed (31 unit, 34 integration, the 2 live tests ignored and not run), `cargo clippy --all-features --all-targets -- -D warnings` clean, `cargo build --no-default-features` builds, `cargo publish --dry-run` packages against the registry.

Left open:

- No change folder was opened for this bump: the delta is the two requirements above, folded straight into cairn/spec/requests.md.
- `GpeopleSend::with_method` traces the request URL with its query at trace level, where io-http 0.7 hides query values in its own debug output.
